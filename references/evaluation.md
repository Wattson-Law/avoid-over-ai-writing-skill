# Cross-Model Evaluation Protocol

Provider adapters are empirical prompt patches. Do not add or broaden one from an anecdote.

## Scope

Record the exact model label, date, product entrypoint, prompt, full response, and terminal status. Describe the result as an operational profile of that model version and entrypoint, not as a permanent provider personality.

## Sampling

For each target language and document type:

1. Give OpenAI/Codex, Gemini, and Claude the same complete prompt.
2. Use the declared model tier and a fresh conversation.
3. Preserve the full response, including artifact notices, prefaces, appendices, progress text, permission blocks, and meta-commentary.
4. Run three source-backed cases and two fresh runs per case.
5. Remove provider names, randomize aliases, and freeze the review packets before reading judgments.
6. Ask each provider to review the other two providers, producing two independent votes per target output.

Do not clean product-entrypoint behavior out of the response. A blocked or abandoned generation is a direct-delivery failure, not a successful sample to retry silently.

## Build A Dataset-Backed Profile Set

Use source records as evidence packets, not as universal style targets.

- For papers, prefer records with explicit claims and supporting evidence, such as `allenai/qasper` or `joelchan/contextualizing-scientific-claims`.
- For patents, prefer real descriptions paired with human abstracts, such as `NortheasternUniversity/big_patent`.
- For technical solutions, prefer real issue-to-patch records, such as `princeton-nlp/SWE-bench_Verified`, and keep the patch hidden from the model as an evaluator-only scope oracle.
- Use synthetic writing datasets only for topic and structure diversity. Do not score all providers against a target generated by one provider.
- Use preference datasets for review design only after checking provenance, label consistency, and license metadata.

Pin every dataset revision and record identifier. Derive a bounded prompt from the source, preserve source facts separately, and record prohibited inferences. Do not copy a reference answer into the prompt.

Keep one unseen source-backed case per document type as a holdout. Do not use holdout outputs to design the adapter.

## Atomic Review

For every output, assign `true` or `false` to each flag and quote one source sentence for every `true`:

- `reopened_position`
- `unsupported_claim`
- `unsupported_effect`
- `invented_scope`
- `overweighted_limitations`
- `defensive_meta`
- `excessive_depth`
- `direct_delivery_failure`
- `required_fact_missing`

Record other factual errors separately. Check reviewer claims against the original prompt because reviewers can misread evidence, word counts, or supplied facts.

For `direct_delivery_failure`, count model-generated artifact announcements, writing notes, research or permission-blocking progress, extra-document commentary, and missing body delivery. Do not count a standalone host-UI timing label such as `Thought for 10s` or `Worked for 1m`; it is not model-controlled prose. Keep the label in the raw response for reproducibility.

## Consensus And Stability

Count a flag on one output only when both blinded reviewers mark it `true`. Keep disagreements as `disputed`; do not resolve them by majority intuition.

Call a failure a document-type tendency only when consensus is `true` in at least four of six outputs and covers all three cases. Call it cross-document only when the document-level threshold is met in at least two document types.

Missing, invalid, quota-blocked, or unavailable reviews never count as agreement. An incomplete matrix may publish only cells that still have exactly two valid votes; label every other cell incomplete.

## Patch Rule

A provider patch must:

- correct a stable provider-specific failure not already handled by the shared workflow
- be limited to the affected document type unless cross-document stability is established
- fit in one short paragraph
- avoid personality labels
- preserve the user's locked position and the supplied evidence
- be removed or revised when later probes do not reproduce the issue

## Regression Test

Rerun the original nine prompts with the shared workflow and matching provider patch, then run the three unseen holdout prompts. A patch passes when:

- the targeted consensus failure decreases
- no supplied evidence or central advantage is removed
- length, format, audience, and required structure still match
- factual errors and direct-delivery failures do not increase
- no new unsupported claim, effect, or scope is introduced
- at least two independent reviewers prefer the revised output for direct delivery

Keep prompts, outputs, mappings, reviews, rejected claims, unavailable-run records, exact patch text, and aggregate files so the result can be reproduced.

# 逻辑结构与内容拆解规范

本规范控制信息顺序，不承担事实审查。所谓“逻辑优化”是把原稿已有内容放到更容易理解的位置，而不是判断内容是否正确。

## 1. 处理强度与结构权限

### format-only

- 保留全部章节和段落顺序；
- 只规范标题层级、编号、列表、表格位置、分页和目录；
- 不合并或拆分有正文内容的段落。

### editorial

- 保留一级章节顺序和既定结论；
- 默认逐段建立“原语义单元 → 输出句子”映射，每个非重复单元必须有且只有一个主要去向；
- 可在同一小节内调整句序、拆分段落、合并碎片句；
- 可把散落的已有依据移到对应结论附近；
- 不删除完整句段来追求简洁。合并内容前必须确认两处语义完全相同，且没有不同的对象、范围、程度、条件、因果、价值或强调作用；
- 不跨一级章节迁移内容，不新增缺失环节。

### restructure

- 仅在用户明确要求时使用；
- 可按选定模式重排已有章节和段落；
- 调整前建立内部“原位置 → 新位置”映射，确保每项信息只移动、不丢失、不扩写为新事实；
- 不为了填满标准结构而补写内容。某一环节缺失时直接省略。

## 2. 需求清单结构

推荐顺序：

1. 文档标题；
2. 项目背景；
3. 需求详情；
4. 按业务场景划分的需求组；
5. 需求组内的条件、功能和输出；
6. 对应识别项或数据表；
7. 供应商方案要求。

每个需求组内部优先按“使用场景/触发条件 → 所需能力 → 输出或响应要求”排列。原稿没有其中某项时不补写。

## 3. 决策方案结构

推荐顺序：

1. 建设背景与决策范围；
2. 现状和核心痛点；
3. 建设目标或核心价值；
4. 评价对象与统一对比维度；
5. 能力、部署、成本和适配性对比；
6. 各方案优势与局限；
7. 原稿既定推荐结论与依据；
8. 实施建议、阶段安排和专项改造说明。

同一批方案使用相同的评价顺序。推荐结论必须保持原稿顺序，不因重排依据而改变优先级。

## 4. 科技研发项目立项申请书结构

保留申报表的固定栏目。常见论证链为：

1. 立项背景；
2. 国内外研究概况及可行性分析；
3. 项目研发目标、关键技术和主要内容；
4. 研究开发方法及技术路线；
5. 项目考核目标和成果形式；
6. 推广应用前景及经济效益；
7. 申报单位、协作单位及分工；
8. 进度、经费、人员和审核意见。

每项研究任务内部按下列已有信息组织：

`工程问题 → 研究对象 → 技术方法 → 模型/模块/平台 → 验证方式 → 成果和指标`

研究目标、研究内容、研究方法和考核指标之间应使用一致的任务名称，但不得为实现形式一致而改写业务范围。

## 5. 科技研发项目实施大纲结构

实施大纲强调执行落地，常见顺序为：

1. 项目的研究意义及必要性；
2. 国内外研究概况及可行性分析；
3. 项目研发目标、创新点和主要研究内容；
4. 总体思路、实施方案及技术路线；
5. 项目考核目标；
6. 项目进度计划；
7. 申报单位和协作单位及分工；
8. 项目经费预算及明细。

实施方案应尽量按工作包组织已有内容：

`任务名称 → 输入/对象 → 研究或实施步骤 → 集成关系 → 验证/应用 → 对应成果`

进度、分工和预算使用原稿已有任务名称，以便阅读者识别对应关系；不推断缺失的责任人或资源。

## 6. 内部追踪矩阵

对 `editorial` 和 `restructure`，内部建立下列映射但不交付：

| 原稿要素 | 目标位置 | 保护要求 |
| --- | --- | --- |
| 问题/需求 | 背景、痛点或研究任务开头 | 不增强严重程度 |
| 方法/措施 | 对应研究内容或实施建议 | 不新增技术路线 |
| 成果/功能 | 对应任务结尾或成果章节 | 不扩大交付范围 |
| 指标/数据 | 原任务或考核章节 | 值、单位、方向原样保留 |
| 主体/分工 | 分工或实施章节 | 不改变责任关系 |
| 结论/优先级 | 结论章节 | 顺序和判断原样保留 |

输出文档中不插入该矩阵，也不生成缺项说明。

## 7. 篇幅保留护栏

- `editorial` 不以压缩篇幅为目标，正文净字符保留率默认不得低于 85%；
- 净字符统计排除目录、页眉页脚、结构编号和纯序号单元格，表格业务内容另行做严格比对；
- 低于 85% 时必须回查被删除或被过度概括的句段并恢复其含义；
- 高于 85% 仍需完成语义映射，字符比例不能证明内容完整；
- 只有用户明确要求摘要、精简或限定篇幅时，才可调整保留率下限。事实、指标、结论和责任边界仍不得改变。
